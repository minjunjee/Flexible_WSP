# 지시문을 가중치로 옮기기: 모델이 갈라지는 자리마다 조건부 편집을 쌓는다

minjunjee, daehanwon. 2026-11-16 draft.

## 요약

지시문을 prompt에 넣지 않고, 훈련도 하지 않고, 가중치만 고쳐서 언어 모델이 출력 형식을 지키게 할 수 있는지 조사했다. 방법은 MLP 출력 행렬에 rank-1 변경을 넣되 답의 특정 자리에서만 켜지게 하는 조건부 편집이다. 편집이 몇 개 필요한지는 편집된 모델 자신의 답을 따라가며 정한다. 지시문 있는 모델과 다음 token 분포가 갈라지는 첫 자리를 찾아 편집을 하나 넣고, 달라진 답에서 다시 찾는다.

Qwen3.5-0.8B에서 JSON 지시문은 편집 둘로 key 이름까지 맞은 답이 94%가 됐다. 지시문을 넣으면 99.6%다. Qwen3.5-4B에서는 편집 셋으로 91%가 됐다. LLM editor 11종이 Gemma 3 4B에서 한 문제도 풀지 못한 IWIBench의 구조화된 응답 과제를 Qwen3.5-0.8B에서 돌리면, 편집을 만드는 문장을 누가 어떻게 썼느냐에 따라 192문제 중 100문제에서 192문제를 풀었다. ABSTRACT_GEMMA

한계도 분명하다. 답의 앞머리로 정해지는 형식에서는 첫 네 token을 강제하는 것과 결과가 같고, 9초 학습한 LoRA가 준수율과 부작용 모두에서 낫다. 답의 끝에서 정해지는 지시문은 옮겨지지 않는다. 그래서 이 방법이 쓰일 자리는 gradient도, prompt도, 생성 과정도 쓸 수 없는 설정이다. 가중치를 직접 고치는 editor가 놓인 설정이 그렇다.

## 1. 문제

언어 모델에게 출력 형식을 정해 주는 가장 흔한 방법은 지시문을 prompt에 넣는 것이다. 이 연구는 같은 효과를 훈련 없이 가중치만 고쳐서 낼 수 있는지를 묻는다. 지시문은 prompt에 없고, 추론할 때 hidden state를 건드리는 hook도 없고, gradient도 쓰지 않는다.

이 질문은 2026년 11월 2일에 나온 Weight-Space Programming 글에서 나왔다. 그 글에서는 LLM이 작은 언어 모델의 가중치를 직접 고친다. 가중치를 고치는 LLM을 editor라고 부른다. 뒤따라 나온 IWIBench는 editor 11종에게 Gemma 3 4B를 고치는 과제 열 가지를 줬다. 그 가운데 구조화된 응답 과제는 지시문 없이 정해진 key를 가진 JSON을 내게 하는 것인데, 모든 editor가 192문제 중 0문제를 풀었다. 가장 잘한 editor는 연습 문장에서는 JSON을 냈지만 질문의 말투가 바뀌자 전부 실패했다. 이 수치는 문헌 조사 agent가 논문 본문에서 읽어 보고한 것이다.

우리가 답하려는 것은 세 가지다.

1. 지시문 하나를 가중치로 옮기는 데 가중치 변경이 몇 개 필요한가. 그 수를 편집을 만들기 전에 잴 수 있는가.
2. 그렇게 센 자리마다 변경을 넣으면 지시문을 넣었을 때만큼 형식이 지켜지는가.
3. 이 방법이 통하지 않는 지시문은 어떤 것인가.

## 2. 관련 연구와 이 연구의 자리

방법을 이루는 부품은 이미 나와 있다. 자세한 조사는 `docs/related_work.md`에 있다.

- steering vector를 MLP 출력 행렬에 rank-1 변경으로 써넣고 특정 조건에서만 켜지게 하는 편집은 arXiv 2604.12359에 있다. 조건은 trigger 단어이고 목적은 backdoor다. steering vector는 추론할 때 hidden state에 더하는 고정된 vector다.
- 마지막 prompt token 자리에만 steering을 걸어도 답의 형식까지 조종된다는 관찰은 arXiv 2610.04967에 있다. 가중치는 그대로 두고 hook으로 한다.
- 지시문이 어떤 자리에는 세게, 어떤 자리에는 거의 작용하지 않는다는 관찰은 arXiv 2605.03907에 있다. 이 논문은 자리마다 세기를 정하는 작은 모델을 학습시킨다.
- 훈련 없이 지시문을 가중치로 옮기는 일은 arXiv 2510.08734가 했다. 답의 모든 자리에서 차이를 한꺼번에 맞추고, 형식 과제는 다루지 않았다.

조사에서 찾지 못한 것이 세 가지다. 지시문 없이, 훈련 없이, 가중치만으로 출력 형식을 지시문 수준으로 지키게 한 결과. 지시문 하나에 편집이 몇 개 필요한지 세는 방법. 그리고 편집 여러 개를 한 모델에 쌓는 방법이다. 이 연구가 다루는 것이 이 세 가지다. 검색으로 찾지 못했다는 뜻이고, 없다는 증명은 아니다.

## 3. 방법

### 3.1 조건부 편집 하나

편집은 MLP의 출력 행렬 W에 vector 두 개의 곱을 더하는 rank-1 변경이다.

```
W' = W + u v^T,    W' h_t = W h_t + (v · h_t) u
```

h_t는 t번째 자리에서 그 행렬에 들어가는 입력, 곧 MLP 안쪽 뉴런들의 값이다. 바뀐 행렬은 원래 출력에 `(v · h_t) u`를 더한다. 그래서 v와 h_t의 곱이 1인 자리에서는 u가 더해지고, 0인 자리에서는 아무것도 더해지지 않는다. 이런 변경을 조건부 편집이라고 부른다. u는 더할 내용이고 v는 언제 더할지를 정한다.

u는 지시문이 그 자리의 hidden state에 만드는 차이다. 같은 질문에 지시문을 붙인 prompt와 붙이지 않은 prompt를 넣고, 편집이 켜져야 할 자리에서 block마다 hidden state의 차이를 구해 질문에 걸쳐 평균 낸다. layer l의 u는 block l 뒤의 평균 차이에서 바로 앞 block 뒤의 평균 차이를 뺀 것이다. 그러면 layer마다 그 layer가 새로 보태야 할 몫만 쓰게 된다.

v는 ridge regression으로 구한다. 지시문 없는 prompt를 넣되 켜져야 할 자리에서 각 layer의 MLP 출력에 u를 더한 채로 모델을 돌리고, 모든 자리의 h를 모은다. 켜져야 할 자리에는 목표값 1을, 나머지 자리에는 0을 주고 h에서 목표값을 맞히는 v를 구한다. 규제 세기는 세 값 가운데 떼어 둔 질문에서 고른다.

이 편집을 모든 layer의 `down_proj.weight`에 하나씩 넣는다. 가중치는 bfloat16 값으로 반올림한다. 편집을 만드는 데 드는 계산은 질문마다 forward pass 몇 번과 layer마다 선형 방정식 하나다.

### 3.2 편집이 몇 개 필요한지 세기

지시문 하나에 편집 하나로 충분하다는 보장은 없다. JSON 지시문에서는 답 시작 자리의 편집 하나로 JSON의 틀은 나왔지만 key 이름은 지시문과 달랐다. 그래서 편집을 넣은 뒤에도 남는 차이를 찾아 편집을 더 넣는 절차가 필요하다.

절차는 편집된 모델 자신의 답을 따라간다.

1. 지금 모델이 지시문 없이 편집용 질문에 답하게 한다.
2. 그 답을 두 모델에 똑같이 넣는다. 하나는 지금 모델이고 다른 하나는 원래 가중치에 지시문을 붙인 모델이다. 답의 자리마다 두 모델이 다음 token에 매기는 확률 분포가 얼마나 다른지를 KL로 잰다.
3. 질문마다, KL이 1 nat을 넘는 첫 자리를 고른다. 두 모델이 다음에 갈라지는 곳이다. 그 뒤의 차이는 여기서 갈라진 결과일 수 있으므로 보지 않는다.
4. 고른 자리들을 묶는다. 지시문 있는 모델이 같은 token을 원하는 자리끼리 묶는 방법과 hidden state 차이의 방향이 비슷한 자리끼리 묶는 방법을 다 해 보고, KL을 합친 값이 가장 큰 묶음을 쓴다.
5. 그 묶음의 자리들을 켜져야 할 자리로 삼아 조건부 편집을 하나 만들어 넣는다.
6. 1번으로 돌아간다. 가장 큰 묶음이 질문의 10%보다 작으면 멈춘다.

편집이 하나 들어갈 때마다 모델의 답이 달라지고, 다음 편집은 달라진 답 위에서 찾는다. 이렇게 넣은 편집의 수가 그 지시문에 필요한 편집의 수다.

편집끼리 서로 망가뜨리지 않게 하는 규칙이 둘 있다. 둘 다 실패를 보고 넣었다.

- 먼저 넣은 편집의 v가 이미 0.5를 넘는 자리는 다시 겨냥하지 않는다. 같은 자리에 편집을 하나 더 넣으면 그 자리의 h가 바뀌고, 바뀌기 전 h에 맞춰 둔 먼저 편집의 v가 더는 1을 내지 않는다.
- 새 편집의 v를 맞춘 뒤, 그 v가 어차피 0.5를 넘는 다른 갈라지는 자리를 묶음에 넣고 편집을 다시 만든다. 편집은 그 자리들을 구별하지 못하므로 u는 그 자리 전부의 평균이어야 한다.

### 3.3 왜 모델 자신의 답을 따라가는가

처음에는 지시문 있는 모델이 쓴 답을 편집된 모델에 넣고 자리마다 KL을 쟀다. 이 방식은 두 가지로 실패했다.

편집된 모델은 지시문 있는 모델과 거의 같지만 조금 다른 token을 쓴다. JSON에서 지시문 있는 모델의 첫 token은 `{"`인데 편집된 모델은 앞에 공백이 붙은 ` {"`를 썼다. 글자로는 같은 JSON이다. 그런데 둘째 편집을 `{"` 뒤의 자리에 맞춰 만들었기 때문에 ` {"` 뒤에서는 켜지지 않았다. key 이름이 맞은 답이 21.8%에 그쳤다.

그리고 같은 자리에 편집을 다시 넣자 유효한 JSON이 83.4%에서 1.2%로 떨어졌다.

모델 자신의 답을 따라가면 두 모델이 같은 token을 쓸 필요가 없다. ` {"` 뒤에서 지시문 있는 모델이라면 무엇을 쓸지를 물으면 된다.

## 4. 실험 설정

**모델.** Qwen3.5-0.8B와 Qwen3.5-4B. 생각 과정은 끈다. Gemma 3 4B는 약관 동의가 필요해서 아직 받지 못했다.

**질문.** 공개 자료로 다섯 유형 664개를 만들었다. 사실 질문, 문장에서 사람이나 장소 뽑기, 두세 자리 덧셈과 뺄셈, 단어 번역, 감상문의 긍정과 부정 가리기다. 앞의 네 유형에서 64개로 편집을 만들고 100개로 비교 대상을 조정한다. 재는 데는 다섯 유형 500개를 쓴다. 감상문 유형은 재는 데만 쓴다. 세 묶음은 겹치지 않는다.

**지시문.** 열세 개다. 열 개는 IFEval의 문구와 통과 기준을 그대로 쓴다. 세 개는 우리가 정했다. `{"answer": "..."}` 꼴의 JSON으로 답하기, 정해진 말로 시작하기, 세 단어 이하로 답하기다.

**비교 대상.** 지시문을 prompt에 넣은 모델이 기준이다. 훈련 없는 기존 방법으로는 차이를 한 layer의 모든 자리에 더하는 steering을 쓴다. layer와 배율은 조정용 질문에서 고른다. 차이를 답 시작 자리에만 hook으로 더하는 것도 잰다.

**재는 법.** 생성은 greedy다. 지시문을 지킨 답의 비율과 답에 정답 문자열이 든 비율을 잰다. 구간은 시험 질문을 다시 뽑는 bootstrap으로 구한 95% 구간이다. 가중치만 바꾼 조건은 hook 없이 잰다. 계산은 float32로 했다. bfloat16으로 계산하면 배치 크기에 따라 greedy 출력이 달라졌기 때문이다.

## 5. 결과

### 5.1 JSON 지시문, Qwen3.5-0.8B

지시문은 `Respond only with a JSON object of the form {"answer": "..."} and nothing else.`다. 시험 질문 500개, 새 token 40개까지다.

| 조건 | 유효한 JSON | key 이름이 answer | 정답 문자열이 들어 있음 |
| --- | --- | --- | --- |
| 편집 없음 | 0.0 | 0.0 | 77.6 [74.0, 81.4] |
| 지시문을 prompt에 넣음 | 99.6 [99.0, 100.0] | 99.6 [99.0, 100.0] | 75.8 [72.0, 79.4] |
| 차이를 한 layer의 모든 자리에 더함 (hook) | 34.6 [30.4, 39.0] | 4.2 [2.6, 6.2] | 50.2 [45.8, 54.6] |
| 차이를 모든 layer의 모든 자리에 더함 (hook) | 12.8 [9.8, 15.8] | 1.6 [0.6, 2.8] | 58.8 [54.6, 63.0] |
| 차이를 답 시작 자리에만, 모든 layer에 더함 (hook) | 96.2 [94.4, 97.6] | 12.8 [10.0, 15.8] | 76.6 [72.8, 80.2] |
| 조건부 편집 하나, 가중치만 | 95.8 [94.0, 97.6] | 14.6 [11.6, 17.8] | 75.8 [72.0, 79.4] |
| 조건부 편집 둘, 가중치만 | 94.0 [91.8, 96.0] | 94.0 [91.8, 96.0] | 76.2 [72.2, 80.0] |
| 대조군 셋, 가중치만 | 0.0 | 0.0 | 68.6에서 77.4 |
| 편집 없이 첫 token을 `{"`로 강제 | 81.8 [78.2, 84.8] | 10.8 [8.2, 13.4] | 63.0 [58.8, 67.2] |
| 편집 없이 첫 네 token을 `{"answer": "`로 강제 | 99.2 [98.2, 99.8] | 99.2 [98.2, 99.8] | 76.8 [73.2, 80.4] |

값은 %다. 조건부 편집 하나는 모든 layer 24개에 rank-1 변경을 하나씩 넣은 것이다. 대조군은 u를 norm이 같은 무작위 vector로 바꾼 것, v의 원소 순서를 뒤섞은 것, 소문자 지시문에서 구한 u를 쓴 것이다.

표에서 네 가지를 읽는다.

**더하는 자리가 결과를 가른다.** 모든 자리에 더하면 layer를 하나 쓰든 전부 쓰든 35% 아래이고 정답도 준다. 답 시작 자리에만 더하면 96%이고 정답은 그대로다.

**가중치 편집은 hook과 같은 일을 한다.** hook으로 더한 96.2%와 가중치만 바꾼 95.8%가 거의 같다. 대조군은 0%다.

**편집 하나는 틀만 옮긴다.** 답 시작 자리의 편집만 넣은 모델은 `{"result": 1615}`, `{"sentiment": "positive"}`처럼 key를 스스로 짓는다. 3.2절의 절차는 여기서 둘째로 갈라지는 자리를 찾았다. ` {"` 바로 뒤, key 이름을 쓰는 자리다. 지시문 있는 모델은 `answer`를 원하고 편집된 모델은 `result`나 `location`을 썼다. 이 자리에 편집을 하나 더 넣자 key 이름까지 맞은 답이 94.0%가 됐다. 그다음에는 질문의 10%를 넘는 묶음이 없어서 절차가 멈췄다. 그러니 이 지시문에 필요한 편집은 둘이다.

**지시문이 하는 일은 답의 앞머리를 정하는 것에 가깝다.** 편집 없이 첫 네 token을 강제하기만 해도 99.2%다. 다만 token만으로는 모자란다. 첫 token 하나만 강제하면 81.8%이고 정답이 63.0%로 떨어진다. 답 시작 자리의 hidden state를 고친 쪽은 95.8%에 정답 75.8%다.

편집 둘을 넣은 모델을 safetensors로 저장하고 새 process에서 `from_pretrained`와 `generate`만으로 다시 쟀다. 500개 중 495개가 글자까지 같은 답이었다.

### 5.2 편집은 앞머리 강제보다 나은가

5.1절의 마지막 관찰은 반론이 된다. 편집이 하는 일이 답의 첫 몇 token을 정해 주는 것뿐이라면, 생성할 때 그 token을 강제로 넣는 것과 다를 바가 없다. 그래서 지시문 열세 개에서 둘을 직접 견줬다. 질문은 시험 질문 가운데 유형마다 40개씩 200개다. 앞머리 강제는 지시문 있는 모델이 쓴 답의 첫 4 token 또는 첫 16 token을 지시문 없는 모델에 넣고 이어 쓰게 한 것이다. 값은 지시문을 지킨 답의 %이고 구간은 95% Wilson 구간이다.

| 지시문 | 지시문을 넣음 | 첫 4 token 강제 | 첫 16 token 강제 | 조건부 편집 | 쌓은 편집 수 |
| --- | --- | --- | --- | --- | --- |
| JSON, key는 answer | 100 | 99 | 100 | 98 [94, 99] | 2 |
| JSON으로 감싸기 | 100 | 66 | 72 | 96 [92, 98] | 3 |
| 제목 붙이기 | 100 | 99 | 100 | 95 [91, 97] | 4 |
| 정해진 말로 시작하기 | 100 | 22 | 100 | 54 [47, 61] | 4 |
| 소문자 | 99 | 45 | 74 | 86 [81, 90] | 3 |
| 대문자 | 98 | 43 | 44 | 79 [73, 84] | 2 |
| 프랑스어 | 98 | 82 | 98 | 88 [83, 92] | 3 |
| 쉼표 쓰지 않기 | 99 | 52 | 64 | 98 [95, 99] | 4 |
| 세 단어 이하 | 98 | 73 | 73 | 94 [90, 97] | 2 |
| 따옴표로 감싸기 | 92 | 49 | 50 | 53 [46, 60] | 1 |
| bullet 세 개 | 100 | 3 | 16 | 26 [21, 33] | 4 |
| 정해진 말로 끝내기 | 70 | 0 | 8 | 0 [0, 2] | 3 |
| 추신 붙이기 | 90 | 0 | 8 | 편집을 만들지 못함 | 0 |

지시문은 세 무리로 갈린다.

**앞머리로 정해지는 형식.** JSON과 제목은 편집이 95%에서 98%다. 그런데 첫 4 token을 강제하기만 해도 99%다. 이 무리에서는 편집이 앞머리 강제를 가중치로 옮긴 것이라는 반론이 맞다.

**답 전체에 걸치는 형식.** 소문자, 대문자, 프랑스어다. 처음에는 여기서 편집이 앞머리 강제를 크게 넘을 것으로 기대했고, 셋 중 둘 이상에서 첫 16 token 강제보다 30%p 이상 높은 것을 기준으로 잡았다. 결과는 소문자 +12%p, 대문자 +35%p, 프랑스어 −10%p다. 기준을 넘은 것은 대문자 하나다. 그러니 이 기대는 맞지 않았다. 다만 지시문을 넣으면 이 모델의 답이 짧아져서 첫 16 token이 답 전체인 문항이 많다는 점은 감안해야 한다. 소문자는 200개 중 167개가 그렇다.

**답의 끝이나 개수로 정해지는 형식.** 정해진 말로 끝내기, 추신 붙이기, bullet 세 개다. 편집도 앞머리 강제도 0%에서 26%다.

기존의 훈련 없는 방법인 steering과도 견줬다. 차이를 한 layer의 모든 자리에 더하고, layer와 배율을 조정용 질문에서 "지시문도 지키고 정답도 든 비율"로 골랐다. 시험 질문 500개에서 steering은 소문자 98%, 쉼표 쓰지 않기 96%, 세 단어 이하 82%, 프랑스어 81%, 대문자 80%로 답 전체형에서는 편집과 비슷하거나 높다. 앞머리형에서는 JSON 0%, 제목 1%, JSON으로 감싸기 22%로 거의 되지 않는다. 그러니 두 방법은 잘하는 곳이 다르다.

### 5.3 지시문이 답의 어디에서 정해지는지 재기

편집이 될지를 편집을 만들기 전에 알 수 있는지 봤다. 지시문 있는 모델의 답을 지시문 없는 모델에 넣고, 그 모델이 다른 token을 골랐을 자리를 센다. 그런 자리의 수를 nD, 마지막 그런 자리가 답의 어디쯤인지를 dL이라고 적는다. dL은 0이면 답의 처음, 1이면 끝이다.

지시문 열세 개에서 dL과 편집 준수율의 Spearman 상관은 −0.56이고 p값은 0.046이다. nD는 −0.53이고 p값은 0.062다. 미리 정한 기준은 −0.6 이하였으므로 조금 못 미친다. dL이 가장 큰 세 지시문은 추신 붙이기, bullet 세 개, 정해진 말로 끝내기로, 편집이 안 된 세 지시문과 정확히 같다.

그래서 말할 수 있는 것은 여기까지다. 답의 끝에서 정해지는 지시문은 이 측정으로 걸러지고, 그런 지시문에서는 편집이 안 된다. 측정값으로 준수율을 맞힌다고 하기에는 모자란다. 제목 붙이기와 정해진 말로 시작하기는 nD가 7.0과 6.3으로 비슷한데 편집 준수율은 95%와 54%다. 편집이 몇 개 필요한지도 이 값으로는 맞히지 못했다. 편집 수와의 상관은 0.43이고 p값이 0.15다.

### 5.5 IWIBench의 구조화된 응답 과제

이 과제는 남이 정한 문제다. 짧은 거주 기록에서 이름을 뽑아 달라는 요청에, 지시문이 없어도 episode마다 정해진 key를 가진 JSON으로 답해야 한다. 통제 문항도 있다. 다른 말투의 요청에서도 내용이 맞아야 하고, 일반 질문에는 평소처럼 답해야 하고, 산문으로 답하라고 하면 산문으로 답해야 한다. 점수는 목표 문항의 성공률에 통제 문항을 지킨 비율을 곱한 것이다. 문항과 채점기는 IWIBench 저장소의 것을 그대로 썼고, 공개된 실험 설정과 같은 episode 셋을 돌렸다. 공개된 editor 11종은 Gemma 3 4B에서 192문제 중 0문제를 풀었다.

우리가 쓴 것은 episode의 목표 문장에 적힌 key 이름과, 우리가 따로 만든 문장이다. 채점 문항은 편집을 만드는 데 쓰지 않았다. 이름을 뽑아 달라는 문장에서는 지시문 있는 모델을 따라야 할 대상으로 삼았다. 산문을 요구하는 문장과 일반 질문에서는 지시문 없는 원래 모델을 따라야 할 대상으로 삼았다. 그러면 그런 문장에서는 갈라지는 자리가 생기지 않아서, 편집이 거기서는 꺼져 있도록 맞춰진다.

| Qwen3.5-4B | 코드를 읽은 뒤 쓴 376개, episode 하나 | 64 / 64 | 1.000 |

### 5.6 훈련을 쓰는 방법과 견주기

같은 행렬에 LoRA를 학습시켰다. rank 4이고, 지시문 없는 질문을 입력으로, 지시문 있는 모델의 답을 목표로 300쌍을 썼다. lr 1e-4로 1 epoch, 38 step이고 학습은 9초 걸렸다.

| 지시문 | 방법 | 준수율 | 정답 | 일반 글에서의 KL |
| --- | --- | --- | --- | --- |
| JSON, key는 answer | LoRA, 9초 학습 | 100 [98, 100] | 72.5 | 0.003 |
| JSON, key는 answer | 조건부 편집 둘 | 98 [94, 99] | 74 | 0.020 |
| 소문자 | LoRA, 10초 학습 | 99 [96, 100] | 58.0 | 0.006 |
| 소문자 | 조건부 편집 셋 | 86 [81, 90] | 52 | 재지 않음 |

짧게 학습한 LoRA가 준수율도 높고 일반 글에서의 부작용도 작다. 그러니 형식 지시문에서는 훈련을 쓰지 않는다는 것이 비용의 이익이 되지 않는다. LoRA는 300쌍으로 학습했고 편집은 질문 64개로 만들었다는 차이는 있다. 64쌍으로 학습한 LoRA는 돌리지 않았다.

### 5.7 부작용과 버티는 범위

**일반 글.** JSON 편집 둘을 넣은 모델에 Wikipedia 글 10만 token을 읽혔다. 편집의 v와 h의 곱이 0.5를 넘은 자리는 없었고 가장 큰 값이 0.11이었다. 다음 token 분포는 원래 모델과 평균 KL 0.020 nat만큼 달랐다.

**긴 문서 뒤.** 질문 앞에 상관없는 문서를 끼웠다. 편집의 준수율은 문서가 없으면 97%, 1,000 token이면 83%, 4,000 token이면 85%, 16,000 token이면 93%다. 지시문을 넣은 쪽은 99%에서 100%를 지킨다. 지시문에서 멀어지면 편집이 유리할 것이라는 기대는 맞지 않았다.

**생각 과정을 켠 prompt.** 편집은 생각을 끈 prompt로 만들었다. 생각을 켜면 모델이 생각을 닫은 뒤의 답 가운데 19%만 유효한 JSON이었다. 지시문을 넣으면 99%다.

**되돌리기.** 편집을 다시 빼도 가중치가 원래 값으로 돌아가지 않는다. 원소의 12%가 달라진 채 남는다. 저정밀 반올림 때문이고 모델 출력의 차이는 KL 2×10⁻⁶ 수준이다. 되돌릴 수 있어야 하면 u와 v를 따로 저장해 두면 된다.

**바뀌는 가중치의 수.** rank-1 변경은 행렬의 거의 모든 원소를 조금씩 바꾼다. 편집 둘이면 MLP 출력 행렬의 원소 8,800만 개 가운데 95%가 바뀐다.

## 6. 무엇이 서고 무엇이 서지 않는가

**서는 것.**

1. 답의 앞머리로 정해지는 형식은 훈련 없이 가중치만 고쳐서 지시문 수준으로 지키게 할 수 있다. Qwen3.5-0.8B에서 JSON 94%에서 98%, 제목 붙이기 95%이고 Qwen3.5-4B에서 JSON 91%다. hook이 없고, 저장한 checkpoint를 다시 불러와도 같은 답이 나온다.
2. 편집을 여러 개 넣으려면 편집된 모델 자신의 답을 따라가며 자리를 찾아야 한다. 지시문 있는 모델의 답에 자리를 맞추면 조금 어긋난 token 하나 때문에 다음 편집이 켜지지 않는다. 같은 종류의 자리를 두 번 겨냥하면 먼저 넣은 편집이 꺼진다.
3. 답의 끝에서 정해지는 지시문에서는 이 방법이 통하지 않고, 그런 지시문은 편집을 만들기 전에 걸러 낼 수 있다.

**서지 않는 것.**

1. 편집이 앞머리 강제보다 낫다는 주장. 앞머리형에서는 첫 4 token 강제와 같고, 답 전체형에서는 대문자 하나에서만 뚜렷이 높다.
2. 훈련을 쓰지 않아서 싸다는 주장. 9초 학습한 LoRA가 준수율도 부작용도 더 좋다.
3. 지시문에서 멀어져도 버틴다는 주장. 긴 문서 뒤에서는 지시문 쪽이 100%를 지키고 편집 쪽이 83%까지 떨어진다.
4. 측정값으로 편집의 성공과 필요한 편집 수를 맞힌다는 주장. 상관이 −0.56이고 지시문이 13개뿐이다.

**그러면 이 방법은 어디에 쓰는가.** 남는 자리는 gradient도 쓸 수 없고 prompt도 생성 과정도 건드릴 수 없는 설정이다. Weight-Space Programming과 IWIBench가 바로 그 설정이고, 거기서는 LLM editor가 아직 형식 과제를 풀지 못했다. 이 연구의 절차는 그 과제를 닫힌 식으로 푸는 한 가지 방법이다. IWIBENCH_DISCUSSION

## 7. 한계

- 대부분의 결과가 Qwen3.5-0.8B 하나에서 나왔다. 4B에서는 JSON 지시문과 IWIBench episode 하나만 돌렸다.
- IWIBench 결과는 편집을 만드는 문장에 민감하다. 문장을 누가 어떻게 쓰느냐에 따라 192문제에서 수십 문제까지 갈린다.
- 편집된 모델은 지시문 있는 모델만큼 확신하지 못한다. 처음 보는 말투에서 첫 token이 조금 어긋나고, 그러면 뒤의 편집이 따라오지 못한다. 답 시작 자리의 편집을 1.25배에서 3배로 키워 봤는데, 이름을 뽑는 문장에서는 나아졌지만 다른 문장에서도 켜져서 합치면 이득이 없었다.
- 쉼표 쓰지 않기에서는 편집이 지시문을 98% 지키게 하지만 정답이 76%에서 48%로 떨어진다. 까닭은 보지 못했다.
- 생각 과정을 켠 prompt, 여러 차례 이어지는 대화, 지시문 여러 개를 같이 넣는 경우는 다루지 못했다.

2. IWIBench를 Gemma 3 4B에서 끝까지 돌리고, 문장을 쓰는 방법을 정해 둔 채로 episode 수를 늘린다.
3. 답 전체형 지시문은 steering을 가중치로 옮기는 쪽이 맞을 수 있다. 항상 켜지는 편집과 자리에서만 켜지는 편집을 한 지시문에 같이 쓰는 방법을 본다.
4. 답의 끝에서 정해지는 지시문에는 "답이 끝나 간다"는 상태를 읽는 v가 필요하다. 생각을 멈추게 하는 편집들이 쓰는 방법과 같은 종류의 문제다.
