# 후보 2 PoC 계획에서 `PLAN.md`에 없는 부분

`PLAN.md`는 Claude 문서 "후보 2 PoC 계획"에서 실험을 돌리는 데 필요한 내용만 옮긴 파일이다. 원래 문서에는 겹치는 최근 연구, 새로 주장할 것의 배경 설명, 출처 목록이 더 있다. 이 파일은 그 부분을 모은 것이다.

2026-11-15에 minjunjee가 채팅에 붙여 넣은 문서 본문에서 옮겼다. 문장은 고치지 않았다. 붙여 넣는 과정에서 표의 칸 구분이 풀려 있어서 표는 다시 짰고, 출처에 걸려 있던 link는 본문에 남아 있지 않아서 옮기지 못했다.

실험 계획과 판정 기준은 `PLAN.md`를 따른다. 두 파일의 내용이 다르면 `PLAN.md`가 기준이다.

## 한눈에

원래 문서의 이 절에는 `PLAN.md`에 없는 문장이 넷 있다.

- 첫 문장 앞에 "새 주장은 이쪽으로 옮긴다."가 있다.
- IWIBench에서는 비슷한 과제인 구조화된 응답을 어떤 editor도 풀지 못했다. editor는 가중치를 고치는 LLM을 가리키고, 그쪽 대상 모델은 Gemma 3 4B다.
- 어떤 지시문은 되고 어떤 지시문은 안 되는 이유가 이 연구의 둘째 질문이다.
- 이익이 가장 클 수 있는 것은 실험 9다. 모델이 답을 써 놓고도 생각을 멈추지 못하는 문제에 같은 방법을 쓴다.

## 겹치는 최근 연구

후보 2를 세 부분으로 나누면 부분마다 이미 누가 손을 댔다. 비어 있는 곳은 한 군데다. 훈련 없이 가중치만 고쳐서 출력 형식을 지시문 수준으로 지키게 만든 결과가 아직 없고, 왜 안 되는지 설명한 연구도 없다.

세 부분은 이렇다. 첫째는 가중치를 고치는 LLM에게 무엇을 보여 주느냐를 바꿔 가며 비교하는 일이다. 이 LLM을 Weight-Space Programming 글에서는 editor라고 부른다. 둘째는 지시문이 없어도 JSON 같은 형식을 지키게 만드는 편집이다. 셋째는 특정 조건에서만 작동하는 편집이다. 표에서는 차례로 보여 주는 것, 형식 심기, 조건부라고 줄여 적는다.

| 연구 | 겹치는 부분 | 이미 한 것 | 안 한 것 |
| --- | --- | --- | --- |
| WSPBench | 보여 주는 것 비교 | LLM이 아니라 작은 ReLU 회로의 고장을 고치는 과제다. 출력만 보게 하면 32개 중 14개, 가중치도 주면 30개를 고쳤다 | LLM을 대상으로 한 비교. 해석된 feature를 주는 조건 |
| WSP Toolkit | 보여 주는 것 | editor용 도구 약 50개를 묶었다. SAE로 만든 feature 색인이 들어 있다 | 색인이 있을 때와 없을 때의 비교 |
| IWIBench | 형식 심기 | Gemma 3 4B에 목표 열 가지를 주고 editor들을 시험했다. 구조화된 응답은 모든 editor가 실패했다 | 실패한 이유. 실제로 되는 편집 |
| SmolLM2 JSON 실험 | 형식 심기 | Claude Code가 SmolLM2-360M의 가중치를 고쳤다. JSON tool 호출 정답률이 20%에서 그대로 20%였다 | 성공한 편집 |
| Stolfo et al. | 형식 심기 | 지시문이 만든 hidden state 차이를 한 layer의 모든 자리에 더했다. 지시문 없이 형식을 지킨 비율이 약 10%에서 약 30%가 됐다 | 가중치 편집. 지시문 수준의 비율 |
| Prompt Baking | 형식 심기 | 지시문 있는 모델의 출력 분포를 따라 하도록 가중치를 학습시켰다 | 훈련 없는 방법. 지시문이 답의 어느 자리에서 작용하는지 |
| Transmuting prompts into weights | 형식 심기, 조건부 | 훈련 없이 최소제곱으로 bias와 행렬을 구해 MLP에 더했다. Gemma 3 1B에서 곱셈과 덧셈 과제는 지시문과 같은 100점, 목록의 첫 항목 고르기는 31.67 대 83.25였다 | 형식 지시문. 편집이 몇 개 필요한지 세기. editor와 묶기 |
| CAST | 조건부 | 입력 내용에 따라 steering vector를 더할지 말지 정했다 | 가중치 편집. 답 안의 특정 자리를 조건으로 쓰기 |
| ROME, BadEdit | 조건부 | 특정 단어가 들어왔을 때만 작동하는 편집을 식으로 계산했다 | 단어가 아닌 답 안의 자리를 조건으로 쓰기 |

표에서 steering vector는 추론할 때 hidden state에 더하는 고정된 vector다. 가중치는 건드리지 않는다. SAE는 hidden state를 사람이 읽을 수 있는 feature 여러 개의 합으로 풀어 주는 작은 network다.

읽은 범위를 밝힌다. IWIBench는 앞선 대화에서 본문까지 읽었고 이번에는 초록만 다시 확인했다. Stolfo et al.과 Transmuting prompts into weights는 본문 앞부분 약 10만 자를 읽었다. 나머지는 저장소 README나 초록을 읽었다.

후속 작업 목록도 다시 봤다. awesome-wsp는 11월 5일 기준 56건이다. SAE나 transcoder를 editor에게 주고 효과를 잰 항목은 없었다. 같은 목록의 비판 글 하나는 LLM 실험에서 editor가 실제로 쓴 것이 날것의 가중치가 아니라 코드와 forward pass였다고 지적한다.

정리하면 이렇다. editor에게 보여 주는 것을 바꿔 비교하는 실험은 작은 network에서 이미 나왔고, LLM으로 옮기는 일은 누구든 곧 할 수 있다. 그래서 이 비교만으로는 새롭다고 하기 어렵다. 조건을 걸어 작동하는 편집의 식도 ROME 때부터 있었다. 새 주장은 다른 곳에 둬야 한다.

## 새로 주장할 것

`PLAN.md`의 주장과 배경 절이 이 절을 줄인 것이다. 아래는 원래 문서에만 있는 문단이다.

자리마다 잰 KL 표 바로 뒤에 이 문장이 있다. 그래서 첫 자리만 바로잡으면 유효한 JSON이 나온다. key 이름까지 맞추려면 둘째 자리에 편집이 하나 더 필요할 것이고, 이것은 아직 돌려 보지 않았다.

편집을 만드는 법은 이렇게 설명한다. 답 시작 자리에서 지시문이 있을 때와 없을 때의 hidden state 차이를 layer마다 평균 낸다. 이 차이를 그 자리에만 더해 주면 된다. 가중치만으로 그렇게 하려고 MLP의 출력 행렬 W에 u와 v 두 vector의 곱을 더한다.

새롭다고 주장할 것의 셋째 항목은 원래 문서에서 숫자가 더 구체적이다. 앞선 대화에서 IWIBench 본문을 읽은 바로는 Astra가 성공시킨 가중치 쓰기 273건이 모두 embedding 행렬에 한 것이었다. 그런 편집은 특정 단어가 들어왔을 때 작동한다. 답 시작 자리는 단어가 아니라 문맥으로 정해지므로 그 방식으로는 겨냥할 수 없다. 이 설명은 내 추측이고 실험 11에서 확인한다.

가장 가까운 연구는 둘이다. Transmuting prompts into weights는 훈련 없이 지시문을 가중치로 옮긴다는 목표가 같다. 다만 모든 자리의 차이를 한꺼번에 최소제곱으로 맞추고, 어느 자리가 중요한지와 편집이 몇 개 필요한지는 따지지 않는다.

Function vector 연구는 vector를 마지막 token 자리의 hidden state에 더한다는 점이 같다. 다만 추론할 때마다 더하는 방식이고 가중치는 그대로 둔다. 이 논문은 초록과 본문 일부만 읽었다.

식 자체는 새롭지 않다. ROME이 사실 하나를 고칠 때 쓰는 rank-1 변경과 같은 꼴이다. 새로운 것은 조건으로 단어 대신 답 안의 자리를 쓰는 것, 그리고 위의 두 가지 측정이다. 이것이 연구 하나의 기여로 충분한지는 실험 5와 6에서 지시문마다 숫자가 실제로 다르게 나오느냐에 달려 있다.

후보 2의 질문은 그대로 남는다. editor에게 무엇을 보여 줄 것인가이다. 후보 답이 하나 늘어난다. 날것의 가중치, feature, 그리고 두 모델이 갈라지는 자리다.
