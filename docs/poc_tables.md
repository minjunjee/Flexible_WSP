# PoC 발표용 숫자

2026-11-16 새벽(KST)에 돌린 결과에서 발표에 쓸 숫자만 뽑았다. 자세한 설명과 나머지 숫자는 `docs/draft.md`와 `results/REPORT.md`에 있다. 생성은 모두 greedy이고, 조건부 편집은 지시문도 hook도 없이 가중치만 바꾼 모델에서 잰 값이다.

## 표 1. JSON 지시문을 가중치로 옮기기

Qwen3.5-0.8B, 시험 질문 500개. 지시문은 `Respond only with a JSON object of the form {"answer": "..."} and nothing else.`다. 구간은 95% bootstrap 구간이다. 출처는 `results/exp1/README.md`다.

| 조건 | 유효한 JSON이고 key가 answer | 정답 문자열이 들어 있음 |
| --- | --- | --- |
| 편집 없음 | 0.0% | 77.6% |
| 지시문을 prompt에 넣음 | 99.6% | 75.8% |
| 차이를 한 layer의 모든 자리에 더함 (기존 steering, hook) | 4.2% | 50.2% |
| 조건부 편집 하나 | 14.6% (유효한 JSON은 95.8%) | 75.8% |
| **조건부 편집 둘** | **94.0%** [91.8, 96.0] | 76.2% |
| 대조군 셋 | 0.0% | 68.6%에서 77.4% |

대조군은 더하는 vector를 무작위로 바꾼 것, read vector의 원소 순서를 뒤섞은 것, 다른 지시문의 vector를 쓴 것이다. 편집 둘을 넣은 모델을 저장했다가 새 process에서 다시 불러오면 500개 중 495개가 글자까지 같은 답을 냈다.

Qwen3.5-4B에서는 같은 절차로 편집이 셋 필요했다. key까지 맞은 JSON이 91.0% [88.6, 93.4]이고 지시문을 넣으면 100%, steering은 18.6%다. 출처는 `results/exp5/qwen35-4b/json_answer/`다.

## 표 2. IWIBench의 구조화된 응답 과제

지시문 없이도 정해진 key를 가진 JSON으로 답하게 모델을 고치는 과제다. 공개된 LLM editor 11종은 Gemma 3 4B에서 목표 문항 192개 중 0개를 풀었다. 이 수치는 문헌 조사 agent가 논문 arXiv 2611.08647의 본문에서 읽어 보고한 것이다. 문항과 채점기는 그 벤치의 것을 그대로 썼다. 점수는 목표 문항 성공률에 통제 문항을 지킨 비율을 곱한 값이다. 출처는 `results/iwibench/README.md`다.

| 모델 | 편집을 만든 문장 | 목표 문항 | 평균 점수 |
| --- | --- | --- | --- |
| Gemma 3 4B, 공개된 LLM editor 11종 | | 0 / 192 | 0 |
| **Gemma 3 4B, 조건부 편집** | 벤치 코드를 보지 않은 다른 모델이 쓴 376개 | **192 / 192** (episode별 64/64, 64/64, 64/64) | **0.958** |
| Gemma 3 4B, 조건부 편집, 고치기 전 절차 | 같은 376개 | 128 / 192 (0/64, 64/64, 64/64) | 0.649 |
| Gemma 3 4B, 조건부 편집, **본 적 없는 test split episode 셋** | 같은 376개 | **74 / 192** (29/64, 0/64, 45/64) | **0.328** |
| Gemma 3 4B, 조건부 편집, test split episode 넷 | 기록 양식을 넓혀 다시 쓴 376개 | **247 / 256** (63/64, 58/64, 64/64, 62/64) | **0.879** |
| Gemma 3 4B, 조건부 편집, development split | 기록 양식을 넓혀 다시 쓴 376개 | **192 / 192** | **1.000** |
| Qwen3.5-0.8B, 조건부 편집 | 같은 376개 | 100 / 192 | 0.494 |
| Qwen3.5-0.8B, 조건부 편집 | 벤치의 문제 생성 코드를 읽은 뒤 쓴 376개 | 192 / 192 | 0.971 |
| 어느 모델이든, 지시문을 prompt에 넣음 | | 192 / 192 | 0.0에서 0.3 |
| 참고: Gemma 3 4B, LoRA 10초 학습, development split | 같은 376개 | 157 / 192 | 0.818 |
| 참고: Gemma 3 4B, LoRA 10초 학습, **test split** | 같은 376개 | **192 / 192** | **1.000** |
| 참고: Gemma 3 4B, LoRA 141 step, development split | 같은 376개 | 192 / 192 | 0.993 |

LoRA 줄은 벤치의 규칙 밖에 있는 참고용이다. 벤치는 editor에게 gradient를 주지 않는다. 그래도 같은 문장으로 학습한 LoRA가 본 적 없는 test split의 192문제를 다 풀었다는 것은, 편집이 거기서 무너진 까닭이 문장이 모자라서가 아니라는 뜻이다. 자세한 표는 `results/followup/tables.md`에 있다.

조건부 편집의 192 / 192는 공개된 실험 설정의 episode 셋(development split)에서 나온 값이고, 이 episode들은 절차를 고치는 데 썼다. 처음 절차로는 한 episode가 0/64였고 그 결과를 보고 절차를 고쳤다. 그래서 발표에서는 본 적 없는 test split의 74 / 192를 같이 말해야 한다.

test split에서 떨어진 까닭은 둘이다.

- 기록의 양식이 다르다. test split의 기록은 `Resident: Greta Rossi. Home city: Bogota.`처럼 항목 이름이 적힌 꼴이다. 편집된 모델은 JSON으로 답하기는 했지만 그 낱말을 key로 가져다 써서 `{"resident": ...}`나 `{"resident_name": ...}`이 나왔다. 첫째와 셋째 episode에서 틀린 답의 대부분이 이것이다. 편집을 만든 문장 192개 가운데 이런 꼴의 기록은 2개뿐이었다.
- key가 token 여러 개로 쪼개진다. 둘째 episode의 key `person_text`는 token 셋이다. token마다 편집이 하나씩 드는데 편집을 넷까지만 쌓게 해 두었고, 가까운 자리의 편집끼리 서로 망가뜨려 `{"person_":Esme Haddad"}` 같은 답이 나왔다. development split의 key는 전부 token 하나였다.

기록 양식을 넓혀 다시 쓴 문장의 줄은 이렇게 읽는다. 편집 방법은 그대로 두고 문장만 바꿨다. 새 문장은 벤치 코드와 채점 문항 없이 썼지만, test split에서 실패를 본 뒤에 "기록의 양식을 고르게 섞으라"고 시켜서 쓴 것이다. 그래서 이 줄은 본 적 없는 episode의 값이 아니다. test split의 넷 가운데 key가 `individual`인 episode 하나만 그 전에 돌린 적이 없고, 거기서는 62/64에 점수 0.928이다.

그 밖에 알아 둘 점이 둘 있다.

- 산문으로 답하라는 문항 8개는 원래 Gemma 3 4B도 채점 기준을 통과하지 못해서 점수의 분모에서 빠진다. development split에서 편집된 모델이 그 문항에 JSON으로 답한 수는 episode별로 0개, 6개, 0개다.
- Gemma 3는 MLP 출력 뒤에 정규화가 있어서 Qwen에서 쓰던 편집을 그대로 넣으면 모델이 망가진다. 더하는 vector를 정규화에 맞춰 바꾸고 세기를 2배로 정했다.

## 표 4. 다른 방법과 견주기

Qwen3.5-0.8B, JSON 지시문과 소문자 지시문, 시험 질문 200개. 출처는 `results/REPORT.md`의 표 1과 E3 절이다.

| 방법 | 무엇이 필요한가 | JSON | 소문자 |
| --- | --- | --- | --- |
| 지시문을 prompt에 넣음 | prompt | 100% | 99% |
| 편집 없이 답의 첫 4 token 강제 | 생성 과정 | 99% | 45% |
| 편집 없이 답의 첫 16 token 강제 | 생성 과정 | 100% | 74% |
| LoRA rank 4, 9초 학습 | gradient, 300쌍 | 100% | 99% |
| LoRA rank 4, 편집과 같은 질문 64개, 40 step | gradient, 64쌍 | 100% | 96% |
| LoRA rank 4, 편집과 같은 질문 64개, 8 step | gradient, 64쌍 | 0% | 18% |
| 모든 자리에 steering (hook), 시험 질문 500개 | 추론할 때 hook | 0% | 98% |
| **조건부 편집** | forward pass와 선형 방정식, 질문 64개 | 98% | 86% |

## 발표에서 같이 말해야 하는 것

- IWIBench의 192 / 192는 절차를 고치는 데 쓴 episode에서의 값이다. 본 적 없는 episode에서는 74 / 192다.
- 앞머리로 정해지는 형식에서는 첫 4 token을 강제하는 것과 결과가 같다. 편집이 강제보다 뚜렷이 높은 것은 대문자 하나다. 대문자는 편집 79%, 첫 16 token 강제 44%다.
- IWIBench에서도 같은 문장으로 10초 학습한 LoRA가 test split 192문제를 다 푼다. 편집은 74문제다. Gemma 3 4B에서 편집을 만드는 데는 episode 하나에 20분에서 30분이 걸린다.
- 9초 학습한 LoRA가 준수율도 높고 일반 글에서의 부작용도 작다. 편집과 같은 질문 64개만 써도 40 step이면 JSON 100%, 소문자 96%다. 일반 글에서 원래 모델과의 KL이 LoRA 0.003, 편집 0.020이다. 그러니 이 방법이 쓰일 자리는 gradient도 prompt도 생성 과정도 쓸 수 없는 설정이고, IWIBench가 그 설정이다.
- 답의 끝에서 정해지는 지시문은 옮겨지지 않는다. 편집을 만들기 전에 재는 값으로 이 세 지시문은 걸러졌다. 그 값과 편집 준수율의 Spearman 상관은 −0.56이고 p값은 0.046이다.
- 질문 앞에 긴 문서가 있으면 편집의 준수율이 97%에서 83%까지 떨어진다. 지시문을 넣은 쪽은 99%에서 100%다.
